## 2. 用户已确认的最终十词

正式词表如下，统一使用小写拼写：

```text
photo
music
open
close
next
previous
start
stop
louder
quieter
```

| 指令 | 已确认功能 | 适用界面 |
|---|---|---|
| photo | 进入照片浏览界面 | 功能入口 |
| music | 进入音乐界面 | 功能入口 |
| open | 将当前选中的照片打开为大图 | 照片列表 |
| close | 退出当前层级：大图返回照片列表；照片列表或音乐界面返回首页 | 当前已打开的界面 |
| next | 下一张照片／下一首音乐 | 照片列表、大图、音乐界面 |
| previous | 上一张照片／上一首音乐 | 照片列表、大图、音乐界面 |
| start | 播放／继续播放音乐 | 音乐界面 |
| stop | 暂停音乐，保留播放位置 | 音乐界面 |
| louder | 增大音量 | 音乐界面 |
| quieter | 减小音量 | 音乐界面 |

注意：上一项使用 `previous`，不再采用讨论中的 `last`；减小音量为 `quieter`，不是 `quite` 或 `quiet`。`open` 的最终用途是打开选中照片的大图，早先“open 直接进入照片浏览”的讨论方案已被替代。

照片交互流程：

1. `photo` 进入缩略图列表，默认选中第一张，使用清晰边框标明当前选中项。
2. `next / previous` 切换选中项。
3. `open` 显示选中照片的大图。
4. 大图中也可用 `next / previous` 翻图。
5. `close` 从大图返回列表，再次 `close` 返回首页。

词语分类与网页操作分开：模型输出词名；网页依据当前页面状态决定操作。照片界面忽略播放、音量指令；音乐界面忽略 `open`。首页的无效指令、大图中重复 `open` 等情况应在实现时给出一致行为。

尚未确认的细节包括：首尾是否循环、音量每次变化幅度、离开音乐界面后是否继续播放、切换歌曲后是否自动播放。不要将这些细节写成用户已确认要求。

## 3. 词表方案与当前程序的区别

2026-10-07 检查源码时，`semg/vocabulary.py` 的默认词仍为 `open、close、next、music`。本次十词确认是实验与产品设计更新，不表示启动程序已经默认显示十词。

开始正式十词采集前，可在主界面“管理词表 / 添加词”中增加 `photo、previous、start、stop、louder、quieter`，保留原四词，并勾选全部十词。检查界面的词表和总试次数再开始录制。

- 本机词表存在项目根目录 `vocabulary.json`，被 Git 忽略；队友 clone 后不会自动得到本机个人词表。
- 每份新录制自带词表和标签映射。跨录制按 `word` 对齐，不把不同录制的数字 label_id 直接当作相同类别。
- 已有四词数据仍可按原词名用于研究；是否合并训练还应核对受试者、动作方式、电极条件及评估划分。
- 不要把旧数据中的词直接改名为新词，不要改写旧录制来伪装十词数据。网页含义调整不改变原来实际录制的发音词。
- 四词模型不会因为词表添加了六个词，就获得识别新词的能力，必须使用包含新类别的训练数据重新训练。
- 测试数据可以包含模型没训练过的词，但当前模型仍只输出其训练类别；没有自动“未知词”拒识。

## 4. 五人十词的采集建议（尚非已完成实验）

此前给出的工程建议是：先做先导采集，再以每人每词 100 次有效试次作为第一阶段目标。这个数量不是 CNN 的理论最低要求，也不保证达到某个准确率。用户已确认十词，尚未确认具体录制日期或最终采集数量。

| 阶段 | 每人每词 | 每人总计 | 五人总计 | 目的 |
|---|---:|---:|---:|---|
| 先导采集 | 20 次 | 200 条 | 1,000 条 | 检查十词动作、信号及流程，初步比较 LDA / 后续 CNN |
| 第一阶段目标 | 100 次 | 1,000 条 | 5,000 条 | 训练小型模型并检验跨批次表现 |
| 按验证结果追加 | 150–200 次 | 1,500–2,000 条 | 7,500–10,000 条 | 判断增加数据是否继续带来收益 |

表中均为累计目标，不是要求每个阶段再额外录同样数量。先导数据只有在协议一致、质量合格且未破坏预定评估划分时才纳入后续数据集。

一条数据指一次完整词语动作试次。2 秒动作里的约 2,000 个采样点仍是一条试次，切成多个窗口也不等于获得多个独立录制。

建议把每词 100 次分为 5 个批次，每批每词 20 次，跨至少 3 天。每批十词共 200 条，沿用轮内随机顺序。按当前准备 1.5 秒、动作 2 秒、休息 2 秒估算，纯试次时长约 18 分 20 秒；加贴电极、基线、检查、休息和补录，每批预留约 25–35 分钟。实际可以按疲劳情况增加休息。

跨天按同一位置规范重新贴电极，记录受试者、日期、Session、电极位置、固定方式及异常。动作定义继续保持：**嘴唇始终闭合，内部尝试发音一次，不出声，之后放松**，不能为了提高分类分数擅自改成张嘴口型或出声。

建议的评估安排：

- 对参与过训练的五个人，按整批划分为 3 批训练、1 批验证、1 批最终测试，所有集合都覆盖十词；最终测试集不要用于反复调参数。
- 若研究新用户泛化，做按人留出评估：四个人用于训练侧，另一个人测试，轮流五次。调参仍需在训练侧独立划分，不能用被留出者的测试成绩选模型。
- 同一试次的所有窗口及其增强版本必须处于同一集合；标准化只拟合训练集。多人混合随机切分不能替代按人留出。
- 当前 GUI 不应被描述为已经具备 CNN 的训练/验证/测试三集合工作流；上述是后续实验设计建议。

参考资料仅用于说明多批次、跨日采集的思路，不把其他硬件或发音方式的成绩套到本项目：

- [SilentWear 数据集说明](https://huggingface.co/datasets/PulpBio/SilentWear/blob/main/README.md)：采用每批每词 20 次及多日采集组织。
- [A Parallel Ultra-Low Power Silent Speech Interface based on a Wearable, Fully-dry EMG Neckband](https://arxiv.org/abs/2509.21964)：包含重新定位设备后的跨批次评估。

## 5. CNN 与网页连接的后续边界

目前只有离线 LDA，没有 CNN 训练功能。LDA 的“八维特征”来自本项目人为选择的表示：动作片段分为四段，每段取 log RMS 和 log 平均绝对相邻差，共 8 维；不是 LDA 必须使用八维。

以后可以比较小型 1D CNN 与 LDA，在相同数据划分下判断是否改善，而不是先承诺 CNN 能解决 music 混淆。单通道中若目标词本身缺乏稳定可区分信息，仅增加网络规模或重复录制不能保证解决问题。

网页接入还需要处理：静息/非指令判断、动作窗口定位、一次动作重复触发、无效页面指令和状态反馈。现有分类器总会从已知类别中选一个，因此不能直接把连续静息信号的预测不加限制地送到网页执行。

此前建议先实现“用户触发识别一次 → 做一次动作 → 输出一个指令 → 网页执行”的演示闭环，再研究持续监听。该方案是建议，尚未实现，也不是要求本次文档更新时立即开发。

共有 80 个完整试次，每词 20 次。原划分为 64 次训练、16 次测试，每词测试 4 次：整体 12/16（75%），music 0/4，其中 2 次判为 open、2 次判为 next。

核查发现 music 确实有 16 次训练样本；重提特征、重建模型和预测与原文件一致，没有发现漏训练、类别索引或保存加载错误。499,960 个原始采样点的二进制回放与 CSV 一致，未发现样本缺口、CRC 错误或 ADC 削顶。数据链路完整不等于已经证明接触正常或信号全部为目标肌电。

保持原八特征和 LDA，20 轮逐轮留出后的结果：

| 词 | 正确数 | 召回率 |
|---|---:|---:|
| open | 13/20 | 65% |
| close | 16/20 | 80% |
| next | 17/20 | 85% |
| music | 11/20 | 55% |
| 整体 | 57/80 | 71.25% |

这是不同划分下的组内诊断，不是改算法后的提升，也不是跨人或跨录制泛化结果。原测试的四个 music 在逐轮验证中仍全部判错。music 与 open 存在双向混淆，同词的幅度和时间形状也有变化；不能仅凭波形确定是动作、接触还是其他因素造成。

诊断只生成新分析文件，没有修改采集程序、源录制、正式模型或原报告；当时核对的原数据和模型文件哈希前后一致。这组数据已经用于诊断，后续据此调参的方案应使用新的独立数据确认。

## 8. 队友安装、串口与界面修复要点

队友应克隆指定分支，进入仓库内 `upper_computer`，先运行 `setup.cmd` 安装，再运行 `start.cmd`。项目根据源码位置定位目录，不依赖作者的 L 盘路径。不要把作者的 `.runtime` 直接复制到另一台电脑使用，应在目标机器创建环境。

当前检查支持 Windows 64 位 Python 3.12–3.14，推荐且实际验证为 3.12；旧接手文档的“Python 3.11 以上”不再是当前安装要求。运行依赖见 `requirements.txt`，开发测试见 `requirements-dev.txt`，额外绘图见 `requirements-analysis.txt`。

此前验证包括 35 项 pytest、模拟采集与训练、含中文和空格的新路径运行，以及深色系统配色下的界面检查。异地目录测试复用了已安装依赖，并不是队友电脑上全新联网安装成功的证明。

串口方面：

- COM4 只是刷新列表时的默认优先选择，不是只能使用 COM4。
- 换电脑或换 USB 口后，Windows 分配的串口号可能变化。插入设备后点“刷新端口”，选择实际设备端口，再“连接 / 检查数据”。
- 无端口时检查对应 USB 串口驱动、数据线和连接；SerialPlot 等程序需先释放端口。
- 采集中先结束并保存，再拔插或换接口；重新连接后再次确认数据就绪。

此前左侧黑色区域来自新增滚动容器继承系统深色背景。v0.4.1 已给侧栏、viewport 和滚动条明确设置浅色背景，并检查深色主题和小窗口截图。不是原始数据或模型的问题；更新后需关闭整个程序再启动。
