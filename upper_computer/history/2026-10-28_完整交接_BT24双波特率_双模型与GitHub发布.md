## 3. BT24 方案与改动

实机发现地址为 `48:87:2D:D0:B5:43`；这是当前模块的观测值，其他模块应扫描后选择，不能固定写死。

| GATT 项目 | 本机实测 |
| --- | --- |
| 服务 | `0000ffe0-0000-1000-8000-00805f9b34fb` |
| 接收通知 | FFE1，支持 notify/read/write/write-without-response |
| 发送 | 优先可写的 FFE1；必要时回退可写 FFE2 |
| Python | Bleak 3.0.2；Windows WinRT 依赖见 requirements-lock.txt |

最初 Windows 能看到设备，但原程序仅接受 COM 串口；队友工具是 Bleak 六列 CSV 联调接收器，不能直接处理原模型二进制协议。初始板子确实输出六列 CSV，5 秒收到 14703 字节而无模型帧。烧录模型固件后，使用原二进制 v2 协议、CRC 和模型身份检查。

主要改动：

- `semg/ble_transport.py`：后台线程与独立 asyncio 循环；扫描、GATT 校验、通知接收、发送分片、有界缓存和队列、连接取消与清理。通知片段交原解码器重组，不假设每个 BLE 通知恰好一帧。
- 修复连接清理竞态：原生 disconnect 独立任务使用 shield，关闭时即使会话取消也等待释放完成，再设置 closed。慢速 disconnect 回归测试曾在修复前失败、修复后通过。
- `semg/board_ui.py`：增加 USB/COM 与 BT24/BLE 选择、异步扫描、连接状态与 UART 提示；BLE 使用合并的 `N\nI\n` 握手。默认监测模型选新版；原采集模式继续保留。
- `app/board_bridge.py`：复用同一个传输模块；维护 connecting/transport/rx_bytes，核对板端版本与 ONNX SHA。只让已验证、启用、无故障的板端确认命令进入媒体分发。
- `app/server.py`：API 版本 3，新增 `POST /api/board/scan-ble`；连接参数支持 `transport=ble`，缺省仍为 serial。
- `app/index.html`、`monitor.js`：扫描/连接操作、连接过程按钮锁定、UART 故障提示、刷新后恢复真实连接设备及波特率。`start.ps1` 拒绝复用旧版本服务。
- `board/check_ble.py`：扫描和被动监听，可选发送身份查询，可指定模型并报告 CRC、序号、包络及耗时。
- 对六列 CSV 明确报固件类型不符，避免将测试流误当成模型结果；断连、复位及故障不会绕过原控制保护。

只让一个程序占用 BT24。桌面监测、网页服务、队友工具和手机不要同时争用同一模块。退出接收程序应正常断开，让 Windows 完成 GATT 释放。

## 4. 双波特率与采样率的关系

统一设置在 `semg/serial_settings.py`：合法值为 **115200、230400**，代码/API 未显式指定时默认仍为 **230400**。当前板子与 BT24 UART 使用 **115200**，因此连接本机板子必须主动选择这一档。

BLE 无线链路本身没有串口波特率；下拉框表达 STM32 ↔ BT24 的 UART 配置。点击选项既不会给模块发送 AT 配置，也不会修改已经烧录的固件。更换波特率需让板端固件、模块 UART 和连接记录一致。

`board/manage.py --baud` 按模型和速率分别构建到 `board/build/<model>/baud_<rate>/`，不覆盖另一档；烧录核对模型、速率和 HEX 哈希。历史默认 230400 的产物仍有兼容路径。原始双路 2 kHz 采集固件继续用 230400，`--capture --baud 115200` 会拒绝。

两档固件仅 UART 初始化值不同；对应模型的权重头文件相同，采样/滤波/归一化/窗口/确认策略不变。常规模型监测约 3920 字节/秒，低于 115200 8N1 的理论字节容量，但这不能证明 BT24 缓存、无线通知和长时间链路不会丢帧。原始波形采集和模型监测属于不同数据流，不能因后者可用 BLE 就宣称训练采集已经支持 BLE。

## 7. 为什么已连接仍不能控制网页

四个条件不同：BLE 连接 ≠ 模型身份通过 ≠ 最新帧无故障 ≠ 板端确认了命令。`top` 只表示当前窗口最高概率类别；`emitted=255` 表示没有命令；“已解锁”只表示允许下一次确认，并不代表刚识别成功。

固件 `board/realtime.inc` 的 `stream_faults` 为锁存故障位：bit 1（值1）TX丢包，bit 2（值2）ADC错误，bit 4（值4）UART错误。UART回调、启动接收或DMA发送失败均可置位4，所以仅凭4无法断定具体是哪一个 HAL 错误。当前 UART ErrorCallback 不执行完整接收恢复。

App 只接受 `verified && enabled && mode==1 && flags==0 && emitted!=255` 的确认结果。故障4时仍显示包络和候选是可能的，网页不执行命令符合保护设计。BLE重连及`N`重置推理流水线不会清掉该故障锁存；STM32复位可清除，但若根因仍在仍可能再次出现，不能把反复复位当作修复。

STM32复位导致时间回退时，App暂停控制并重新请求身份，通过后仍需手动启用。保持无故障并放松到静息解锁后，再做完整 `photo` / `music` 等口型，观察“最近板端确认”；没有确认时不应让候选直接驱动页面。
